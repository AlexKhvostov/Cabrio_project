# Стандарты и соглашения для backend CabrioRide

## 1. Общие принципы
- Минимум сложностей, максимум читаемости и предсказуемости
- REST для сущностей (таблицы), RPC для сложных действий
- Все проверки доступа — только по роли (role), не по статусу
- Строгое разделение id (числовой идентификатор) и code (строковый код)
- Все поля таблиц возвращаются в ответе, связанные сущности — вложенными объектами

## 2. Именование
- `id` — только числовой идентификатор
- `code` — строковый код (role, status, type и т.д.)
- `role` — всегда строковый код роли ("member", "admin" и т.д.)
- `role_id` — числовой идентификатор роли
- `status` — только для авто, событий и других сущностей, не для пользователей
- `status_id` — числовой идентификатор статуса

# Авторизация, структура запроса и ответа, работа с токенами

## 3. Принципы авторизации
- Вся авторизация строится на токенах (JWT или session token).
- Токен — единственный способ идентификации пользователя для всех защищённых эндпоинтов.
- Права доступа определяются только по роли пользователя (role), которая содержится в токене и/или в базе.
- Вся логика проверки прав централизована (см. config/sectionGroups.php).

## 4. Получение токена

### 4.1. Через Telegram-бота
- Бот получает токен у backend при каждом защищённом запросе.
- Токен не хранится между сессиями и не сохраняется в базе бота.
- Процесс:
  1. Пользователь пишет боту.
  2. Бот отправляет запрос на `/api/auth/telegram-bot` с telegram_id (и, если нужно, username).
  3. Backend возвращает токен (JWT/session token).
  4. Бот использует этот токен для защищённого запроса (подставляет в Authorization).
  5. Backend проверяет токен и права пользователя.

**Плюсы:**
- Нет лишней сложности, не нужно хранить токены.
- Безопасно: токен всегда свежий.
- Легко масштабировать: если функций станет больше, можно добавить хранение токенов без изменений в backend.
- Совместимо с WebApp и другими клиентами.

**Минусы:**
- При большом количестве обращений может быть лишняя нагрузка на backend (для простого бота не критично).

**Пример (псевдокод):**
```php
// Получить токен
$response = http_post('/api/auth/telegram-bot', [
    'telegram_id' => $telegram_id
]);
$token = $response['data']['token'];

// Использовать токен для защищённого запроса
$headers = [
    'Authorization: Bearer ' . $token,
    'Content-Type: application/json'
];
$data = http_get('/api/protected-endpoint', [], $headers);
```

### 4.2. Через Telegram WebApp
- WebApp получает данные пользователя через Telegram (initData).
- WebApp отправляет эти данные на backend (`/api/auth/telegram`).
- Backend проверяет подпись Telegram, возвращает токен.
- WebApp сохраняет токен (например, в localStorage) и использует его для всех запросов.

## 5. Формат запроса
- Заголовки:
  - Content-Type: application/json (всегда)
  - Authorization: Bearer <token> (если требуется авторизация)
- Тело запроса:
  - Всегда JSON-объект
  - Обязательные поля зависят от эндпоинта (см. документацию к API)

**Пример:**
```http
POST /api/users
Content-Type: application/json
Authorization: Bearer <token>

{
  "first_name": "Иван",
  "last_name": "Иванов",
  "role_id": 3,
  "email": "ivan@example.com"
}
```

---

## 6. Формат ответа
- Обязательные поля:
  - success (boolean)
  - data (object/array/null) — тело ответа
  - error (object/null)
  - pagination (object, если это список)

**Пример успешного ответа:**
```json
{
  "success": true,
  "data": {
    "id": 123,
    "first_name": "Иван",
    "last_name": "Иванов",
    "role": {
      "id": 3,
      "code": "member",
      "name": "Участник",
      "description": "Подтверждённый член клуба"
    },
    "status": {
      "id": 1,
      "code": "active",
      "name": "Активен",
      "description": "Пользователь активен"
    },
    "city": "Москва",
    "photos": [
      { "id": 1, "url": "https://example.com/photo1.jpg", "description": "Аватар" },
      { "id": 2, "url": "https://example.com/photo2.jpg", "description": "На встрече клуба" }
    ],
    "created_at": "2024-05-01T12:00:00Z"
  },
  "error": null
}
```

> Важно: если возвращается раскрытый объект (role, status и т.д.), отдельные *_id не дублируются на верхнем уровне. Id всегда доступен внутри объекта (например, role.id).

**Пример ошибки:**
```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректные данные",
    "details": { "email": "Некорректный формат email" }
  }
}
```

**Тело ответа (data):**
- Всегда полный объект/массив сущности
- Для связанных справочников (роль, статус, тип и т.д.) — раскрытый объект с id, code, name, description

---

## 7. Проверка прав
- После проверки токена backend извлекает роль пользователя.
- Для каждого эндпоинта/действия определена минимальная роль (см. config/sectionGroups.php).
- Backend сравнивает роль пользователя с требуемой.
- Если роль подходит — действие выполняется, иначе возвращается ошибка доступа.

---

## 8. Системные запросы
- Для действий, инициируемых системой (например, автоматическое повышение роли), используется либо специальный "system" токен, либо внутренний вызов без токена, но с логированием.
- В логах всегда фиксируется, что действие совершено системой.

---

## 9. Совместимость и масштабируемость
- Такая схема полностью совместима с WebApp, мобильными приложениями и любыми другими клиентами.
- Если потребуется хранить токены для оптимизации — backend не нужно менять, только добавить хранение на стороне клиента (бота, WebApp).

---

## 10. Рекомендации
- Всегда использовать токен для всех защищённых запросов.
- Не хранить токены в боте, если функций мало — получать их на каждый запрос.
- При увеличении числа функций/нагрузки — перейти к хранению токенов в базе или сессии.
- Всю логику проверки прав централизовать на backend.

## 12. Системные запросы с SYSTEM_TOKEN
- Для выполнения автоматических или сервисных действий (например, массовое обновление, интеграции, миграции) используйте системный токен из .env (SYSTEM_TOKEN).
- Пример запроса:
  ```http
  POST /api/system-action
  Authorization: Bearer <SYSTEM_TOKEN>
  Content-Type: application/json

  {
    "action": "update_roles",
    "params": { ... }
  }
  ```
- На backend обязательно проверяйте, что токен из заголовка совпадает с SYSTEM_TOKEN из .env.
- Такие запросы должны логироваться как системные действия.

## 14. Передача значений справочников в запросах
- Во всех запросах, где требуется указать значение из справочника (role, status, event_type, car_brand и т.д.), передавайте только строковый code (например, "moderator", "active", "meetup", "bmw").
- Backend ищет id по code в соответствующем справочнике и применяет нужное значение.
- В ответах API возвращается раскрытый объект (id, code, name, description).

**Примеры запросов:**

Изменение роли пользователя:
```http
PUT /api/users/123/role
Content-Type: application/json
Authorization: Bearer <token>

{
  "role": "moderator"
}
```

Создание события с типом:
```json
{
  "event_type": "meetup"
}
```

Добавление авто с маркой:
```json
{
  "car_brand": "bmw"
}
```

**Почему это важно:**
- Фронтенд не зависит от id, которые могут отличаться между окружениями.
- Запросы легко читать и отлаживать.
- Меньше риска ошибиться (например, перепутать id разных справочников).

## Работа с файлами (uploads/)

### Где хранятся загружаемые файлы
- Все загружаемые файлы (фото и др.) хранятся в папке `uploads/` в КОРНЕ проекта.
- Внутри `uploads/` — вложенные папки по типу сущности:
  - `uploads/users/avatars/` — аватары пользователей
  - `uploads/users/gallery/` — дополнительные фото пользователей
  - `uploads/cars/` — фото автомобилей
  - `uploads/guide_objects/` — фото гид-объектов
  - `uploads/events/` — фото событий
  - (при необходимости — другие папки для новых сущностей)
```
uploads/
├── users/             # Файлы участников
│   ├── avatars/        # Аватарки
│   └── gallery/        # Фотографии
├── cars/               # Файлы автомобилей
├── guide_objects/      # Файлы гид-объектов
└── events/             # Файлы мероприятий
```

### Шаблон имени файла
- Формат: `{entity_type}_{entity_id}_{photo_id}.{ext}`
  - `entity_type` — тип сущности (user, car, event, review, guide_object и т.д.)
  - `entity_id` — ID сущности, к которой относится фото
  - `photo_id` — уникальный ID фото (из таблицы photos)
  - `ext` — расширение файла (jpg, png и т.д.)

**Примеры:**
- Аватар пользователя: `users/avatars/user_1_12.jpg`
- Фото авто: `cars/car_7_45.png`
- Фото события: `events/event_3_22.jpg`
- Фото гид-объекта: `guide_objects/guide_object_5_18.jpg`
- Фото для отзыва: `reviews/review_10_33.jpg`

### Какой путь хранится в БД
- В таблице `photos` поле `url` хранит относительный путь к файлу относительно папки `uploads/`.
- Пример значения поля `url`: `users/avatars/user_1_12.jpg`
- В API всегда возвращается полный путь: `/uploads/users/avatars/user_1_12.jpg`

### Назначение фото (photo_type)
- В таблице `photos` есть поле `photo_type` (varchar, опционально):
  - Возможные значения: `avatar`, `cover`, `gallery`, `main`, `document` и т.д.
  - Используется для различения типа фото (например, главное фото, галерея, обложка и т.д.)
  - Для аватара пользователя: `photo_type = 'avatar'`
  - Для главного фото авто: `photo_type = 'main'`

### Как определяется главное фото
- Главное фото для сущности — запись с максимальным `id` в таблице `photos` для данной пары (`entity_type`, `entity_id`) и нужного `photo_type` (например, `main` или `avatar`).
- Для галереи — выбираются все фото с нужным `entity_type` и `entity_id`, кроме главного.

### Примеры для разных сущностей
- **Пользователь**
  - Аватар: `users/avatars/user_1_12.jpg`, `photo_type = 'avatar'`
  - Галерея: `users/gallery/user_1_13.jpg`, `photo_type = 'gallery'`
- **Автомобиль**
  - Главное фото: `cars/car_7_45.jpg`, `photo_type = 'main'`
  - Галерея: `cars/car_7_46.jpg`, `photo_type = 'gallery'`
- **Событие**
  - Обложка: `events/event_3_22.jpg`, `photo_type = 'cover'`
- **Гид-объект**
  - Главное фото: `guide_objects/guide_object_5_18.jpg`, `photo_type = 'main'`
- **Отзыв**
  - Фото: `reviews/review_10_33.jpg`, `photo_type = 'main'`

### Важно
- Все пути к файлам в БД и API — ОТНОСИТЕЛЬНЫЕ к папке `uploads/`.
- Папка `uploads/` всегда должна находиться в корне проекта.
- Для новых типов сущностей/фото — добавлять новые подпапки и значения `photo_type` по аналогии.
