# План построения файловой системы backend CabrioRide

## 1. Анализ и фиксация требований
- Перечитать и зафиксировать все бизнес-требования и технические стандарты (готово, см. документацию).
- Убедиться, что структура backend покрывает все ключевые сущности и бизнес-логику.

## 2. Базовая структура каталогов и файлов
- controllers/ — контроллеры для REST и RPC
- actions/ — бизнес-логика и сложные действия
- models/ — работа с БД, ORM/ActiveRecord
- routes/ — маршрутизация (api.php)
- utils/ — вспомогательные классы (ResponseHelper, AuthHelper, Logger и др.)
- docs/ — документация backend (CONVENTIONS, ENDPOINTS, ENVIRONMENT, openapi.yaml)
- _tests/ — интеграционные тесты
- logs/ — логи приложения
- uploads/ — загружаемые файлы (фото и др.), с вложенной структурой по типу сущности (см. PROJECT_STRUCTURE.md):
  - uploads/users/avatars/
  - uploads/users/gallery/
  - uploads/cars/
  - uploads/guide_objects/
  - uploads/events/

## 3. Создание и описание ключевых классов
- Controllers: для каждой сущности (User, Car, Event, GuideObject, Review, Photo и т.д.)
- Actions: для сложных операций (например, TransferOwnershipAction)
- Models: для каждой таблицы БД
- Utils: ResponseHelper, AuthHelper, ValidationHelper, Logger, Database





## 4. Документирование зависимостей
- Для каждого класса/модуля — кратко описать, от чего он зависит (например, UserController зависит от User, Role, AuthHelper, ResponseHelper и т.д.)
- В документации (CONVENTIONS.md или отдельный файл) добавить схему зависимостей (можно в виде списка или диаграммы).

## 5. Документирование работы с файлами
- Описать:
  - Где хранятся загружаемые файлы (uploads/ в корне проекта)
  - Как формируется имя файла (шаблон: `{entity_type}_{entity_id}_{photo_id}.{ext}`)
  - Какой путь/URL хранится в БД (относительный к uploads/)
  - Где фиксируется назначение фото (`photo_type` в таблице photos)
  - Примеры для разных сущностей (user, car, event и т.д.)
